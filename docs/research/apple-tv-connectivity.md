# Build the remote on infrared first

The simplest viable remote for a current Apple TV 4K is **an infrared transmitter that sends Apple's own NEC-variant codes**. It needs no pairing, no MFi and no radio certification, and the electronics are a tiny microcontroller, one IR LED and seven buttons on 2xAAA. **Bluetooth LE HID over GATT is the strong second choice.** It is the only option that also removes line of sight, and a non-MFi composite BLE HID device is documented working on Apple TV 4K from tvOS 17.4 through tvOS 27.0. In exchange it needs a one-time pairing, an RF module, and a RED declaration and Bluetooth SIG listing if the remote is ever sold. HDMI-CEC works for navigation but needs an always-on box on the HDMI bus plus a second link to the handheld. Network control (Companion/MRP) works but rests on private, reverse-engineered crypto protocols that break across tvOS releases. HomeKit, Matter and Thread cannot send d-pad navigation at all. One thing applies to every transport: no source directly confirms that a non-Siri-Remote input fires SwiftUI `onMoveCommand`, `onExitCommand` and `onPlayPauseCommand` in a third-party app such as Antuna. Apple's documentation and the way these inputs behave system-wide make it very likely, but it is the first thing to check on real hardware.

## Four of six transports can send the seven buttons

The owner needs up, down, left, right, select, back/menu and play/pause, both in the tvOS UI and inside Antuna, where up/down changes channel, back exits and play/pause pauses. The table below shows what each transport can deliver according to the research notes. "System-wide" means the transport drives the tvOS focus engine and Home screen. "In app" means the input should reach the SwiftUI command handlers.

| Transport | System-wide navigation | Reaches Antuna's handlers | User setup | Handheld hardware | Main risk |
|---|---|---|---|---|---|
| IR, native Apple codes (`EE 87`) | Yes (Siri Remote's own IR codes replayed on ATV 4K 2021) | Very likely; unverified | None on an unpaired box | MCU + IR LED, about 10–14 parts | Line of sight; no 2024–26 first-hand report |
| IR, Learn Remote | Yes (Apple-documented) | Very likely; unverified | One on-screen learning pass | Any stable IR protocol | Line of sight; setup step |
| BLE HID over GATT | Yes (UC test table, tvOS 17.4; working on tvOS 27.0) | Likely; unverified | Bluetooth pairing in Settings | nRF52 module + buttons | Reconnect latency; pairing quirks with old ESP32 libraries |
| HDMI-CEC | Yes for arrows/OK/back (stb-tester) | Likely for nav; play/pause uncertain | Enable CEC on TV and Apple TV | Always-on HDMI bridge + separate remote link | tvOS 26.x CEC regressions |
| Companion/MRP (network) | Yes (pyatv HID codes) | High confidence (same path as iPhone remote) | PIN pairing | Pi bridge in practice; no MCU client exists | Private protocol breaks after tvOS updates |
| HomeKit / Matter / Thread | No | No navigation; at most play/pause of the now-playing session | Home app | Thread/Matter button | No navigation action exists |

Apple's own API documentation frames the app-side question well. `onMoveCommand` responds to "an arrow key on a Mac keyboard, or taps the edge of the Siri Remote", and `onExitCommand` fires "by pressing the Menu button on tvOS" ([Apple: onMoveCommand](https://developer.apple.com/documentation/swiftui/view/onmovecommand(perform:)); [Apple: onExitCommand](https://developer.apple.com/documentation/swiftui/view/onexitcommand(perform:))). Apple's WWDC 2016 tvOS session states that **"presses can also be generated from programmable universal remotes and also from Bluetooth keyboards"**, and that directional presses come from "game controllers, keyboards, or IR remotes" ([WWDC16 session 210 transcript](https://asciiwwdc.com/2016/sessions/210)). This is old guidance, but it is still the canonical statement that IR and keyboards feed the same press pipeline as the Siri Remote. One caveat applies whatever transport is chosen: developers report `onMoveCommand` sometimes missing the first press after a view loads on tvOS 18 ([Apple Developer Forums 764582](https://developer.apple.com/forums/thread/764582)). That is a SwiftUI issue, not a remote issue, but it will show up during channel-zapping tests.

## Native Apple IR codes need zero setup and the least hardware

Every Apple TV 4K generation has an IR receiver. Apple's spec page lists "IR receiver" for both 2022 models, including the Wi-Fi-only one, and every Siri Remote generation carries an IR transmitter ([Apple Support 111839](https://support.apple.com/en-us/111839); [Apple Support 103233](https://support.apple.com/en-us/103233)). Apple TVs decode **Apple's NEC variant: 38 kHz, standard NEC timing, address bytes 0xEE 0x87, then a command byte and a "pair ID" byte**. The command's least significant bit is a parity bit over the command and the ID ([Wikipedia: Apple Remote](https://en.wikipedia.org/wiki/Apple_Remote); [hifi-remote.com IRP](https://hifi-remote.com/forums/viewtopic.php?p=149457)). The most useful code table comes from a Flipper capture of the Siri Remote (A2540) on an Apple TV 4K 2021, with pair ID 0x8C. The codes are **Up 0x0A, Down 0x0C, Left 0x09, Right 0x06, Select 0x5C, Back/Menu 0x03 and Play/Pause 0x5F**, plus TV/Home and power codes on address `E5 87` ([Flipper-IRDB Apple_TV_4K_Gen2.ir](https://github.com/Lucaslhm/Flipper-IRDB/blob/main/Streaming_Devices/Apple/Apple_TV_4K_Gen2.ir)). Because the Siri Remote emits these frames itself, the Apple TV's receiver is plainly decoding them on modern hardware. Separate Select and Play/Pause codes exist, so the owner's two distinct buttons map cleanly.

User setup is nil in the common case. Apple lists the old IR-only Apple Remotes as compatible with "any Apple TV", with "functionality might be limited". In a January 2023 MacRumors thread, several owners report old white and aluminum Apple Remotes working on 2021 and 2022 Apple TV 4K units "without programming or linking" ([Apple Support 103233](https://support.apple.com/en-us/103233); [MacRumors](https://forums.macrumors.com/threads/does-the-old-apple-remote-work-with-new-apple-tv.2377099/)). One Apple Community post disagrees, saying older remotes don't work "correctly" with the 4K ([Apple Community 253183476](https://discussions.apple.com/thread/253183476)). One undocumented risk follows from this. If the box was ever IR-paired to a specific Apple Remote ID, frames with a different pair ID could be ignored. Copying the Siri Remote's ID 0x8C is the obvious hedge. If native codes misbehave, **Apple's documented fallback is Settings > Remotes and Devices > Learn Remote**, which accepts any stable IR protocol after an on-screen learning pass ([Apple TV 4K User Guide, tvOS 26](https://support.apple.com/guide/tv/atvb0410f604/26/tvos/)). So the IR path has a built-in plan B that needs no firmware change.

The hardware is minimal: an 8-pin MCU (CH32V003 or ATtiny), a 940 nm LED, a transistor driver, a couple of resistors and capacitors, seven switches and a battery holder. That is roughly 10–14 parts, with no antenna or RF layout. The firmware must emit the full 32-bit Apple frame. Dedicated NEC encoder chips force byte 4 to be the inverse of byte 3, which breaks Apple frames, and they are mostly legacy broker stock anyway ([All About Circuits forum](https://forum.allaboutcircuits.com/threads/suggestions-for-an-ir-codec-ic.120143/)). A common hobbyist trap is that ESPHome switched NEC to LSB-first in 2021.12, so older Apple code configs need bit reversal ([Home Assistant Community](https://community.home-assistant.io/t/ir-change-in-nec-what-do-i-need-to-do/365840)). Power is dominated by standby: a CH32V003 sleeps at about 7–11 µA with correct pin handling, and floating pins push it to about 100 µA ([element14](https://community.element14.com/technologies/embedded/b/blog/posts/low-cost-microcontrollers-using-a-ch32v003-risc-v-device); [ch32v003fun standby example](https://git.c3pb.de/ahorn/ch32v003fun/-/raw/e44c7f40c297c76ed6d457cb85977f01742cab8a/examples/standby_autowake/README.md)). By the notes' estimate, about 10 µA standby plus 200 presses a day costs roughly 110 mAh a year, which is years on 2xAAA. A CR2032 is a poor fit because IR LED peaks around 100 mA collide with its 15–30 Ω internal resistance ([applied-ee BLE power guide](https://applied-ee.github.io/embedded/docs/networking/bluetooth-ble/ble-power-optimization/)).

Certification is where IR clearly beats every radio option. IR light is not radio, so in the EU the remote falls under EMC, RoHS and battery rules by self-declaration, not RED. That scope is the notes' own analysis and should be checked before any sale. In the US, **47 CFR §15.103(h) exempts battery-only digital devices whose highest clock is below 1.705 MHz**, which an MCU at 1 MHz with a 38 kHz carrier satisfies ([47 CFR 15.103](https://www.law.cornell.edu/cfr/text/47/15.103)). The costs of IR are real but narrow. It needs line of sight to the box's front window, which fails if the Apple TV sits behind the TV. Harmony users after tvOS 13 also reported flaky IR wake from sleep, fixed by sending Menu/Home first ([MacRumors tvOS 13 thread](https://forums.macrumors.com/threads/tvos13-remote-doesnt-wake-apple-tv.2201251/)). The newest first-hand report of native Apple IR codes is from January 2023, so nothing confirms tvOS 26 behavior specifically.

## Bluetooth HID removes line of sight at the cost of pairing and paperwork

The best evidence for BLE is Unfolded Circle's per-usage test of its Remote Two/3, a generic non-MFi composite HID device (keyboard, consumer control and system control), on an Apple TV 4K running tvOS 17.4. Keyboard arrows navigate, Return selects and Escape goes back. On the consumer page, **Menu Up/Down/Left/Right (0x42–0x45) navigate, Menu Pick (0x41) selects, Menu Escape (0x46) and AC Home (0x223) both act as Back, and Play/Pause (0xCD) works**. AC Back (0x224) does not work, and volume and mute were untested ([Unfolded Circle AppleTV.md](https://github.com/unfoldedcircle/core-api/blob/main/doc/bt/devices/AppleTV.md)). UC later switched its shipped profile from keyboard arrows to consumer Menu codes because they "work better in YouTube & search", which suggests keyboard arrows get eaten as text-cursor keys when a text field has focus ([UC profile commit history](https://github.com/unfoldedcircle/core-api/commits/main/doc/bt/profiles/appletv.json)). For Antuna's search screens, consumer codes are the safer default. AC Home (0x223) needs a 16-bit consumer usage field, because 8-bit report arrays crop it to 0x23 ([TI E2E forum](https://e2e.ti.com/support/wireless-connectivity/bluetooth-group/bluetooth/f/bluetooth-forum/384465/how-to-send-2byte-consumer-control-code-in-hidadvremote)). The approach is still alive on current software: in October 2026 a Remote 3 owner on tvOS 27.0 reported that when network control failed, **"switching the remote to Bluetooth mode for the Apple TV works normally"** ([integration-appletv #189](https://github.com/unfoldedcircle/integration-appletv/issues/189)). Function101 also sells a commercial BLE edition of its button remote on 2xAAA for about USD 30–40, which shows the category ships ([Best Buy listing](https://www.bestbuy.com/product/function-101-button-remote-for-apple-tv-bluetooth-black/JJGY6ZZZ3F)).

Setup is a single pass through Settings > Remotes and Devices > Bluetooth, optionally with a four-digit code ([Apple Support 102227](https://support.apple.com/102227)). The practical friction is in the firmware stack, not tvOS. The old ESP32-BLE-Keyboard Arduino library drew "plenty of reports with apple devices rejecting it" ([T-vK #44](https://github.com/T-vK/ESP32-BLE-Keyboard/issues/44)). The lower-risk route is a NimBLE or Zephyr/nRF Connect HID build with LE Secure Connections, Just Works bonding, a short ASCII name and bond keys kept in flash. Any consumer key wakes the Apple TV from standby, and UC measured **about 2 seconds from remote wake to a ready, subscribed link** ([UC tracker #65](https://github.com/unfoldedcircle/feature-and-bug-tracker/issues/65)). That latency shapes the power design. A pre-certified nRF52 module such as the Raytac MDBT42Q (about USD 6–10) sleeps at about 0.3 µA in System OFF. Staying connected with a long interval and slave latency averages roughly 5–15 µA, which secondary figures put at about a year or more on a CR2032 and years on 2xAAA ([Raytac/Adafruit](https://www.adafruit.com/products/4077); [applied-ee](https://applied-ee.github.io/embedded/docs/networking/bluetooth-ble/ble-power-optimization/)). Disconnecting when idle saves more battery, but then the first channel press after a pause arrives a second or two late. The ESP32-C3 suits a USB-powered prototype but not a battery remote: its datasheet gives 5 µA deep sleep, while one custom board measured about 300 µA ([esp32.com](https://esp32.com/viewtopic.php?p=81530)).

Certification is heavier than for IR, though it is irrelevant for a single personal build that is never placed on the market. A sold BLE remote needs its own RED Declaration of Conformity covering safety, EMC (EN 301 489-1/-17) and radio, and a pre-certified module's EN 300 328 reports can be reused if it is installed per its instructions ([Microchip conformity guide](https://onlinedocs.microchip.com/oxy/GUID-9E8FA63D-EDB0-4DC2-AB0C-B3693CFF2928-en-US-8/GUID-1386C656-5F4B-4B89-8F12-05767481739F.html)). EN 18031 cybersecurity (from 1 August 2025) likely does not apply. The ADCO guidance treats a standalone Bluetooth device with no internet path, such as Bluetooth headphones, as out of scope, provided the manufacturer's risk assessment says so ([ADCO RED guidance v01.02.2026](https://digital.gob.es/content/dam/portal-mtdfp/avance-digital/telecomunicacion-e-infraestructuras-digitales/areas_interes/equipos-telecomunicacion/documents/Guia-interpretacion-Equipo-conectado-Internet.pdf)). In the US, the module's grant covers the radio but the host still needs a Part 15B SDoC ([FCC KDB 996369 slides](https://fcc.gov/sites/default/files/32-KDB-996369-Modules-TCB_Oct_2023.pdf)). Bluetooth SIG qualification is also required for sale; its fee was not verified in the research.

## CEC and network control work but are not simple

HDMI-CEC does carry navigation. stb-tester, a commercial test tool, drives Apple TV from a USB CEC adapter with **Up, Down, Left, Right, OK, Back, TV and Play**. As of tvOS 17.5, though, CEC Power no longer wakes the box, so KEY_TV has to be used for wake ([stb-tester Apple TV manual](https://stb-tester.com/manual/appletv.html)). The catch is architectural. CEC lives on the HDMI cable, so a hobbyist remote needs an always-powered bridge such as a Raspberry Pi (all models have CEC) on the HDMI chain, and then a second wireless link from the handheld to that bridge ([Home Assistant HDMI-CEC](https://www.home-assistant.io/integrations/hdmi_cec/)). Play/pause is the weak spot, because stb-tester lists only Play and it is unknown whether that toggles or reaches `onPlayPauseCommand`. Users also report CEC regressions in tvOS 26.x on Sony and LG setups ([Apple Discussions 256204616](https://discussions-cn-prz.apple.com/thread/256204616)). Apps have no CEC API ([Apple Developer Forums 70875](https://developer.apple.com/forums/thread/70875)). The zero-hardware variant, the TV's own remote over CEC, is worth trying first because it costs nothing, but it is not a custom remote.

The network route offers the full button set. The Companion protocol's HID codes cover Up 1, Down 2, Left 3, Right 4, Menu 5, Select 6, Home 7 and Play/Pause 14, after a one-time PIN pairing ([pyatv protocols](https://pyatv.dev/documentation/protocols/)). Because it emulates the iPhone Control Center remote, it is the input most likely to reach Antuna's handlers unchanged. It is also the least simple. Companion uses HAP-style SRP pairing, X25519/Ed25519 keys, ChaCha20-Poly1305 and OPACK framing, and **no microcontroller implementation exists**; Arduino forum threads report no success ([Arduino forum](https://forum.arduino.cc/t/arduino-apple-tv/1287315)). It has broken repeatedly: at tvOS 13, at tvOS 15 when MRP moved inside AirPlay, at 18.4, and reportedly again at tvOS 26 ([pyatv supported features](https://pyatv.dev/documentation/supported_features/); [simon42 community](https://community.simon42.com/t/apple-tv-mediasteuerung-funktioniert-nicht/67597)). A battery Wi-Fi remote doing pair-verify on every wake is a poor power fit, so the realistic form is a Pi running pyatv with a dumb button remote talking to it.

HomeKit, Matter and Thread are dead ends for navigation. Apple TV is a Matter controller, home hub and Thread 1.4 border router in tvOS 26, not a controllable Matter media device ([Matter Alpha](https://www.matteralpha.com/news/apple-tv-upgrades-to-thread-1-4-with-tvos-26-beta); [MacRumors](https://www.macrumors.com/2025/06/13/tvos-26-beta-thread-1-4-support/)). Matter Casting's Keypad Input cluster is implemented on Fire TV, and Apple TV does not appear in any source ([Amazon Matter Casting](https://developer.amazon.com/docs/fire-tv/overview-of-matter-casting.html)). Through the Home app, Apple TV exposes power and Siri-level play/pause, which at most reaches Antuna's now-playing session if the app publishes `MPNowPlayingInfo` and handles `MPRemoteCommandCenter` ([Apple Support 108393](https://support.apple.com/en-kz/108393)). A Thread button's battery life is attractive, but it has no path to `onMoveCommand`.

There is one option outside Apple's protocols. Because the owner controls Antuna's source code, the app itself could listen on the LAN while in the foreground (for example over UDP via Network.framework) and accept channel up/down, back and pause from an ESP32. This works only inside Antuna, needs a local-network permission prompt and is not backed by any source in the research. It is a fallback if a transport fails to deliver `onPlayPauseCommand`, not a first choice.

## Bench tests that decide the build

The research leaves a short list of open questions that only a real Apple TV 4K on tvOS 26 can answer. Add a debug overlay to Antuna that logs every `onMoveCommand` direction, `onExitCommand`, `onPlayPauseCommand` and raw UIKit `pressesBegan` type. That one change answers most of the open questions for every transport at once.

| # | Test | Why it is open |
|---|---|---|
| 1 | Send the A2540 IR table (`EE 87`, pair ID 0x8C) from an MCU and confirm all seven buttons in the tvOS UI with no setup | Latest first-hand report is Jan 2023; tvOS 26 untested |
| 2 | Repeat test 1 inside Antuna: Up/Down change channel, 0x03 fires `onExitCommand`, 0x5F fires `onPlayPauseCommand` | No source confirms IR presses reach SwiftUI handlers |
| 3 | Try a second pair ID (for example 0x8B with the 0x0B family) to check that an unpaired box accepts any ID | Pair-ID enforcement on tvOS is undocumented |
| 4 | Hold Up/Down: compare NEC repeat frames (every 108 ms) with firmware-generated discrete presses for channel zapping | Auto-repeat behavior with `onMoveCommand` is unknown |
| 5 | Wake the Apple TV from long sleep with IR Back/Menu and with `E5 87` TV and Power-on codes | IR wake was flaky after tvOS 13; per-model wake untested |
| 6 | Learn Remote with a plain-NEC code set, then repeat test 2 | Fallback path; learned-button list and app delivery unverified |
| 7 | Measure IR range and angle with the box behind or beside the TV, on 2xAAA | Placement determines whether IR is acceptable at all |
| 8 | Pair an nRF52 BLE HID build (consumer 0x41–0x46, 0xCD, 16-bit usages); repeat tests 2 and 4 | UC table is tvOS 17.4 and never tested SwiftUI handlers |
| 9 | Compare Escape vs 0x46 vs 0x223 for Back, and keyboard arrows vs 0x42–0x45, on Antuna's list and search screens | Different back codes and text-field arrow capture |
| 10 | Measure BLE first-press latency after idle disconnect and the connected idle current the Apple TV actually grants | Apple TV may override requested slave latency; about 2 s reconnect reported |
| 11 | Confirm the bond survives a battery swap and an Apple TV reboot | Reconnect after hours of sleep is unreported |
| 12 | If CEC is considered: send CEC Play (0x44) and Pause (0x46) from a Pi and check `onPlayPauseCommand` | Only Play is listed; tvOS 26 CEC regressions reported |

## Conclusion

The question was framed as a choice among connectivity standards, but the decision is mostly about placement and paperwork. If the Apple TV is in view of the couch, native Apple IR wins on every axis the owner cares about: no setup, the fewest parts, years on AAA and essentially no certification. Learn Remote covers the case where native codes misbehave. BLE HID becomes the right answer only if the box is hidden. The best build plan is therefore to prototype on IR first (tests 1–7), and to plan the BLE board in parallel only if test 7 shows line of sight is a problem. A seven-button BLE remote with IR for TV power is also what Function101 already sells for about USD 35, so a hobby IR build is cheap to try before committing to radio.

The larger uncertainty sits in the app, not in the transport. Every viable path ends in the same unproven step: a non-Siri-Remote press reaching Antuna's SwiftUI handlers, with play/pause the least certain. The debug overlay costs an afternoon and turns the whole comparison from inference into measurement. If play/pause fails on the chosen transport, the owner can still route it through Antuna's own code, either by handling `MPRemoteCommandCenter` or with a LAN listener. Third-party remotes on other platforms rarely have that option.
